# Changelog

## 2.13.0 (2026-10-21)

Agents check every change in a real browser, and the agent guard protects the developer's machine, a Mac first.

- Browser checks by agents (`testing.md`): every change to a screen, user flow or public route is checked in the running app before the review, in every profile (Feature workflow step 7). The lead turns the acceptance criteria into steps; the `test-runner` runs them and reports each step with console errors, failed requests and screenshots. A failed step goes back to the code's owner as a failing test; a check stuck twice goes to the `designer` (the lead in lean). The browser check finds and the test suite keeps: anything worth repeating becomes a test, and nothing from the check is committed. Projects without a UI skip it.
- The tool is Microsoft's Playwright CLI (`@playwright/cli`): a development dependency pinned to an exact version, run from the project's own copy as a shell command, so the guard, the permission rules and the sandbox apply. `.playwright/cli.config.json` starts the installed Google Chrome, which keeps itself patched, with a fresh in-memory profile (none of the developer's sign-ins, and never the macOS Keychain), and allows only the local app's origin. Its vendor skill is not installed (it advises global `@latest` installs and browses outside sites), and its update notice is hidden (`NO_UPDATE_NOTIFIER=1` in the settings template). The Playwright MCP server, its marketplace plugin and Claude in Chrome are not used; `agents.md` gives the reasons.
- Screenshots: the designer takes them with the browser CLI (light and dark, mobile and desktop, seeded data only), and the lead attaches them to the PR with `gh pr create --attach`. The PR template has a checklist item for the browser check.
- Seeded development accounts (`backend.md`): one per role on `.test` addresses, sharing a `DEV_SEED_PASSWORD` that is random on each machine and never committed; the seed refuses an empty password or a database that is not local. Development servers and local services listen on 127.0.0.1 only (`security.md`).
- Agent guard, for every agent including the lead: Playwright CLI commands only within the browser check's rules (local addresses; an allowlist of page commands, so `attach`, `show`, `run-code`, installs and commands a newer version adds are denied; no saved profiles, other config files or `PLAYWRIGHT_*` settings; files inside the project; no `npx`, `bunx` or `dlx` downloads); shell commands that name a path in the project's Read deny rules; Keychain reads (`security find-generic-password` and the like); and web addresses opened in the developer's own browser (`open`, `xdg-open`). It asks the lead before `osascript` and installs outside the project (`npm install -g`, `brew install`, `pipx install`, `pip install --user`), and denies both for subagents. `decide()` takes the project root whose settings hold the deny rules. Its tests cover each rule and every browser command `testing.md` shows.
- Deny rules: Claude Code's own login file (`~/.claude/.credentials.json`) and the Context7 CLI's key files are added. Guardrails now says what the rules cover: Claude's file tools only, so a shell `cat ~/.ssh/id_ed25519` used to get past them; the guard now denies it, and the strict sandbox blocks it as well.
- Context7 (`agents.md`, Tools): an optional extra a developer may add for themselves, never set up in the project. It is installed from the official plugin marketplace at user scope and signed in through `/mcp`, with no API key in files or the environment. The free plan has 1,000 calls a month and blocks, never bills, when they run out; agents use the stack-conventions skill first, record each library's Context7 ID there so a lookup takes one call, write what they learn into the skill, and fall back to the official docs without retries when refused. Its answers are leads to confirm on the official page.
- Strict profile: on Linux the browser CLI is excluded from the sandbox, since a sandboxed command's localhost is private there; on macOS it stays sandboxed if Chrome starts there, which checkpoint D proves.
- Trusted sources: Claude Code's MCP page and the Playwright CLI docs.
- Skill: unchanged; the saved skills need no update.
- Projects: in upgrade mode, replace `scripts/quality/`; merge the settings template's `env` and deny rules into `.claude/settings.json`; update `.claude/agents/test-runner.md` and `designer.md`; add the Browser checks by agents section to `docs/TESTING.md`, the Browser and Documentation lookups bullets and the guard and deny-rule changes to `docs/AGENT-TEAM.md`, the development accounts to `db:seed` and `docs/DATABASE.md`, the 127.0.0.1 rule to `docs/security/THREAT-MODEL.md`, and the Commands row, the Tests and Agents lines and steps 7 and 10 to the root `CLAUDE.md`; add the PR template's checklist item; then install `@playwright/cli` pinned, write `.playwright/cli.config.json` and add `.playwright-cli/` to `.gitignore`.

## 2.10.0 (2026-10-21)

- Agent guard: new script `scripts/quality/agent_guard.py`, run by Claude Code as a PreToolUse hook before every shell command (`templates/claude/settings.json`). It denies git writes by subagents (only the lead commits, pushes, switches branches or changes the index; Claude Code tells the hook which agent runs a command), skipped hooks (`--no-verify`, `commit -n`, `core.hooksPath`, `LEFTHOOK=0`), force pushes other than `--force-with-lease` to a feature branch, force-pushing or deleting `main`, pushing to `main` once the remote has it, and the promote script run by a subagent. It asks the user, even in auto mode, before merging a pull request, creating or changing the remote repository, changing the git host through its API, promoting to production without `--dry-run`, and commands that discard uncommitted work across the tree. It sees through `&&`, pipes, `bash -c`, `$(...)`, wrappers such as `env` and `timeout`, and ignores here-document bodies and quoted text; a git command it cannot read is denied. Each decision is explained to the agent and logged to `logs/agent-guard.log`; `--command` shows the decision for one command. Its tests prove that every git command in the Feature, Hotfix and Release workflows passes. It takes about 25 ms per command.
- Deny rules in the settings template stop Claude from reading SSH keys, cloud and git host logins, key and certificate files, and service account keys.
- Guardrails (`agents.md`): the guard and deny rules apply in every profile; they are seatbelts, and branch protection and CI stay the walls for `main`. Claude Code's sandbox stays off by default in lean and standard, because it gets in the way of Docker, the local database, browser tests and setup downloads; developers can turn it on with `/sandbox`. The strict profile requires it, with exclusions written from the Commands table and proven in checkpoint D, Docker Compose allow rules for the commands that only start, stop, inspect or enter containers, and bypass-permissions mode disabled.
- Memory (`agents.md`): a table of what the team remembers, who writes it and how long it lives. `.claude/plan.md` names its branch on its first line, a plan for another branch is replaced and never resumed, and the plan is deleted after the merge. Project facts live in the repository; when Claude Code's auto memory disagrees, the repository wins.
- Loop limits: an agent that ends without its report, for example at its turn limit, counts as failed and is never sent the same task unchanged. A command the guard blocks is reported, never retried in another form (`implementer`, `debugger`).
- Development keys (`security.md`): development uses its own provider keys with low spending caps, and the local `.env` never holds staging or production secrets, because agents read the whole project folder.
- Root `CLAUDE.md` template: the Agents line, a Keeping-these-rules line on auto memory, a Commands row for the guard, and Feature step 11 deletes the plan file after a merge. Scaffold progress: checkpoint A writes the settings, checkpoint D verifies the guard and, in strict, the sandbox. Upgrade mode adds the guard to the safety net. Trusted sources list Claude Code's hooks, permissions, sandboxing and memory pages.
- Skill: the plan covers the agent guardrails, and the tools check includes `bubblewrap` and `socat` for the strict sandbox on Linux. The saved claude.ai skill needs updating.
- Projects: in upgrade mode, replace `scripts/quality/`; merge the `permissions.deny` rules and the `hooks` block from `templates/claude/settings.json` into `.claude/settings.json`; check that `.gitignore` has `logs/`; move any staging or production secrets out of local `.env` files; update the Guardrails, Memory, How work flows, Loop limits and Verification gates sections of `docs/AGENT-TEAM.md`, `.claude/agents/implementer.md` and `debugger.md`, the Agents line, the auto memory line, the Commands row and Feature step 11 in the root `CLAUDE.md`, the configuration line and tools table in `docs/security/THREAT-MODEL.md`, and the AI coding tools row of `docs/SOURCES.md` (then `python3 scripts/quality/sources.py sync`). It records the conventional and the currently recommended way per topic, the project's choice where they differ, and the traps (old APIs that still look plausible), each with its source and date. The `implementer`, `reviewer`, `debugger`, `designer` and `architect` preload it; it is refreshed on major upgrades and in the quarterly `chore(agents)` review.
- New `designer` agent (Opus, high, no edit tools): proposes layout, components, states, feedback and accessibility for new screens at planning time, and reviews every change to the project's UI paths at Feature step 8, in parallel with the `reviewer` and within the same single review round.
- New `architect` agent (Opus, xhigh, no edit tools, can fetch the trusted sources): consulted only for a new architecture pattern, a framework or major-version migration, a core dependency, or a choice where the conventional and recommended ways differ. It returns options with sources and dates and drafts the ADR; routine features do not use it.
- `references/agents.md` gains the Stack expertise and UI work sections; the lean profile keeps the designer for new screens only and drops the architect. The root `CLAUDE.md` template's Agents line and Feature steps 2, 4 and 8 name the new agents. Tests check that the advisory agents cannot edit, that coding agents preload the skill, and the skill template's structure.
- Projects: in upgrade mode, copy `designer.md` and (standard and strict) `architect.md` into `.claude/agents/`, add the `skills` preload to the existing `implementer`, `reviewer` and `debugger`, write `.claude/skills/stack-conventions/SKILL.md` from the official docs for the installed versions and add those pages to `docs/SOURCES.md` (then `sources.py sync`), list the UI paths in `docs/AGENT-TEAM.md`, and update the root `CLAUDE.md` lines.

## 2.2.0 (2026-10-18)

- Agent team: new reference `references/agents.md`, which becomes `docs/AGENT-TEAM.md`. The main session leads on Opus at `xhigh` effort, writes the plan to `.claude/plan.md` and delegates slices to specialist agents: `implementer` (Opus, high), `test-runner` (Haiku, low, in the background), `reviewer` (Opus, xhigh, fresh context, no edit tools), `debugger` (Opus, high) and, on the strict profile, `security-auditor` (Opus, max). Agents report only to the lead, in one shared format with the evidence for their status.
- Loop limits: two attempts per failure before an agent stops as `blocked`, a `maxTurns` limit on every agent, one review round that re-checks only its own findings, test results reused for an unchanged commit, and one owner per slice and per file.
- Agent teams stay off in project settings and are enabled per session only for parallel review, competing-hypothesis debugging and multi-layer features with separate files.
- New templates in `templates/claude/`: `settings.json` pins the lead's model and sets its effort through `modelSettings` (a top-level `effortLevel` is ignored by Opus 5.5 and later), and `agents/` holds the five agent definitions. New test `tests/test_agent_templates.py` checks their frontmatter, the read-only roles, the report format, the roster table and the lead settings.
- The root `CLAUDE.md` template gains an Agents line, and Feature steps 7 and 8 and Hotfix step 1 name the agents. The scaffold progress checklist copies `.claude/` in checkpoint A and ignores `.claude/plan.md`. `references/sources.md` lists the Claude Code documentation for keeping models and effort levels current.
- Projects: in upgrade mode, write `docs/AGENT-TEAM.md`, copy `templates/claude/agents/` to `.claude/agents/` (keeping the roles the profile needs), merge `model` and `modelSettings` from `templates/claude/settings.json` into `.claude/settings.json`, add `.claude/plan.md` to `.gitignore`, add the Claude Code rows to `docs/SOURCES.md` and run `sources.py sync`, and update the root `CLAUDE.md` lines.

## 2.1.0 (2026-10-16)

- Trusted sources: new reference `references/sources.md`, which becomes `docs/SOURCES.md`. It lists the official and curated sources for versions, support windows, advisories, malicious packages, platform limits, security practice, SEO, privacy law and email, in order of trust, filtered to each project's stack and countries. It also says when Claude consults them (scaffold, every new dependency, releases, hotfixes, an optional weekly agent) and treats fetched pages as data, never instructions. The skill and the Feature, Hotfix and Release workflows now check these sources instead of relying on memory.
- New check script `scripts/quality/sources.py` (`check`, `sync`, `domains`): keeps Claude Code's WebFetch allow rules in `.claude/settings.json` in step with the sources file. It never pre-approves wildcards or hosts where anyone can publish, flags http links, and warns when the list's review date is older than `sources.reviewDays`. New `sources` section in `quality.config.json`; the hook template runs the check.
- Legal documents (`privacy.md`): terms of service and what they cover, versioned legal documents, explicit acceptance at sign-up recorded per version, re-acceptance after material changes, minimum age, and duties for apps that host user content. The privacy policy is shown, not agreed to.
- Local development and promotion: development never uses a hosted project; everything a hosted project needs lives in the repository; one idempotent promote script (`deploy:env`, with `--dry-run`) takes it to staging and production. Commands are listed for Postgres, Supabase and Firebase. A data-store family rule says which moves are scriptable (within Postgres-compatible stores, or local and hosted Firebase) and which are a data-layer rewrite (across families).
- Security: CORS policy, incoming and outgoing webhooks, bot protection with a challenge on public forms, an edge proxy with DDoS protection and a WAF with the origin locked to it, the client IP read only from the trusted proxy's header, and a new supply-chain section (frozen installs, minimum release age and update cooldowns, install scripts only for trusted packages, incident response). A lean section lets VPN-only internal tools skip the WAF and the bot challenge.
- Email (`hosting.md`): a local mail catcher, a staging allowlist, SPF, DKIM and DMARC, separate transactional and marketing streams, one-click unsubscribe, bounce and complaint handling.
- Templates: new lines in the root `CLAUDE.md`, the scaffold progress and launch checklists, and the PR template for all of the above.
- Projects: in upgrade mode, replace `scripts/quality/`; add the `sources` section to `quality.config.json`; write `docs/SOURCES.md` and run `sources.py sync`; add the `trusted-sources` hook job; then adopt the new rules as PRs: legal documents and terms acceptance, the promote script, email authentication, edge protection, CORS, webhooks and supply-chain settings.
