# Changelog

## 2.10.0 (2026-10-21)

- Agent guard: new script `scripts/quality/agent_guard.py`, run by Claude Code as a PreToolUse hook before every shell command (`templates/claude/settings.json`). It denies git writes by subagents (only the lead commits, pushes, switches branches or changes the index; Claude Code tells the hook which agent runs a command), skipped hooks (`--no-verify`, `commit -n`, `core.hooksPath`, `LEFTHOOK=0`), force pushes other than `--force-with-lease` to a feature branch, force-pushing or deleting `main`, pushing to `main` once the remote has it, and the promote script run by a subagent. It asks the user, even in auto mode, before merging a pull request, creating or changing the remote repository, changing the git host through its API, promoting to production without `--dry-run`, and commands that discard uncommitted work across the tree. It sees through `&&`, pipes, `bash -c`, `$(...)`, wrappers such as `env` and `timeout`, and ignores here-document bodies and quoted text; a git command it cannot read is denied. Each decision is explained to the agent and logged to `logs/agent-guard.log`; `--command` shows the decision for one command. Its tests prove that every git command in the Feature, Hotfix and Release workflows passes. It takes about 25 ms per command.
- Deny rules in the settings template stop Claude from reading SSH keys, cloud and git host logins, key and certificate files, and service account keys.
- Guardrails (`agents.md`): the guard and deny rules apply in every profile; they are seatbelts, and branch protection and CI stay the walls for `main`. Claude Code's sandbox stays off by default in lean and standard, because it gets in the way of Docker, the local database, browser tests and setup downloads; developers can turn it on with `/sandbox`. The strict profile requires it, with exclusions written from the Commands table and proven in checkpoint D, Docker Compose allow rules for the commands that only start, stop, inspect or enter containers, and bypass-permissions mode disabled.
- Memory (`agents.md`): a table of what the team remembers, who writes it and how long it lives. `.claude/plan.md` names its branch on its first line, a plan for another branch is replaced and never resumed, and the plan is deleted after the merge. Project facts live in the repository; when Claude Code's auto memory disagrees, the repository wins.
- Loop limits: an agent that ends without its report, for example at its turn limit, counts as failed and is never sent the same task unchanged. A command the guard blocks is reported, never retried in another form (`implementer`, `debugger`).
- Development keys (`security.md`): development uses its own provider keys with low spending caps, and the local `.env` never holds staging or production secrets, because agents read the whole project folder.
- Root `CLAUDE.md` template: the Agents line, a Keeping-these-rules line on auto memory, a Commands row for the guard, and Feature step 11 deletes the plan file after a merge. Scaffold progress: checkpoint A writes the settings, checkpoint D verifies the guard and, in strict, the sandbox. Upgrade mode adds the guard to the safety net. Trusted sources list Claude Code's hooks, permissions, sandboxing and memory pages.
- Skill: the plan covers the agent guardrails, and the tools check includes `bubblewrap` and `socat` for the strict sandbox on Linux. The saved claude.ai skill needs updating.
- Projects: in upgrade mode, replace `scripts/quality/`; merge the `permissions.deny` rules and the `hooks` block from `templates/claude/settings.json` into `.claude/settings.json`; check that `.gitignore` has `logs/`; move any staging or production secrets out of local `.env` files; update the Guardrails, Memory, How work flows, Loop limits and Verification gates sections of `docs/AGENT-TEAM.md`, `.claude/agents/implementer.md` and `debugger.md`, the Agents line, the auto memory line, the Commands row and Feature step 11 in the root `CLAUDE.md`, the configuration line and tools table in `docs/security/THREAT-MODEL.md`, and the AI coding tools row of `docs/SOURCES.md` (then `python3 scripts/quality/sources.py sync`). Strict projects add the sandbox block and verify every command still runs.

## 2.8.0 (2026-10-21)

- Roadmap: new template `templates/ROADMAP.md`, which becomes `docs/ROADMAP.md` in checkpoint A. It lists the confirmed plan's features in build order, each a thin vertical slice that fits one PR: first what others depend on, then the riskiest unknowns, then the rest by value. Rows have fixed ids (`R7`, parts `R7a`) and the statuses `planned`, `split`, `dropped` and `done (#14)`. The branch (`feat/r7-...`) and the PR description (`Roadmap: R7`) carry the id, and right after opening the PR the lead sets the row to `done (#14)`, so the row and the PR link to each other. When the user names no feature, the lead proposes the first ready row; the feature report names the next one.
- Feature size (`git-workflow.md`): a PR changes at most about 400 lines and 10 files of source code, not counting tests, docs, generated migrations and lockfiles. A bigger feature is split into parts with the user's approval, by what a user can do rather than by layer, each part mergeable and deployable alone. Unfinished parts merge behind release flags: one typed `flags` module, set per environment and changed only with a deploy, checked on the server in every entry point the part adds, and removed by the last part; release flags are kept apart from the safeguard breakers.
- Agents (`agents.md`, `implementer`): slices running in parallel check only their own files (their tests, lint, and the type checker's errors in them); project-wide commands run only while no implementer works, and the `test-runner` runs the full `check` once all slices are done. A slice that changes the schema, a dependency or shared configuration runs alone first. The worktree rule now gives the current reason (subagent worktrees start from the default branch, or with `worktree.baseRef: "head"` from the last commit, which misses uncommitted slices), and the Claude Code worktrees page is a trusted source.
- Root `CLAUDE.md` template: the Git and Agents lines, and Feature steps 1, 4 (the split replaces the separate "more than ~10 source files" approval trigger), 9, 10 and 11. The PR template gets a `Roadmap:` line and a size checklist item; upgrade mode adds the roadmap with the repository workflow.
- Skill: the plan lists the features in build order, and the final report names the first ready one. The saved claude.ai skill needs updating.
- Projects: in upgrade mode, add `docs/ROADMAP.md` from the template with the features still planned; add the Feature size section to `CONTRIBUTING.md` and change its branch-name line; update the Git and Agents lines and Feature steps 1, 4, 9, 10 and 11 in the root `CLAUDE.md`, How work flows and Verification gates in `docs/AGENT-TEAM.md`, step 4 of `.claude/agents/implementer.md`, the PR template, and the AI coding tools row of `docs/SOURCES.md` (then `python3 scripts/quality/sources.py sync`).

## 2.7.0 (2026-10-20)

Code checks permissions (`can(actor, 'marker.delete', marker)`), never role names; permissions and each role's set live in one typed catalog in code, and role assignments in the database, with several roles per user. Ownership is a separate check. The first admin is created by a server command; nobody grants permissions they lack or changes their own roles; the last admin stays; role changes rotate sessions, are audited and notify. - Profiles: the append-only audit log and required MFA for admin and staff accounts move from strict to standard (`security.md`, `backend.md`); strict adds an audit log copy the app cannot change, fresh checks for admin actions, an admin area behind an access proxy, and a second admin for lifting takeover locks.
- Links from `security.md`, `logging.md`, `hosting.md`, `architecture.md`, `privacy.md` and `upgrade.md` (spending caps come first in an upgrade); the root `CLAUDE.md` template gets a Safeguards line and Feature steps 3, 4, 6, 8 and 9 ask about cost and the safeguards table; the scaffold progress checklist builds roles and safeguards in checkpoint B and verifies them in D; the launch checklist gets a Safeguards and spending section; the `reviewer`, `security-auditor` and PR template check the same. ## 2.6.0 (2026-10-20)

- Privacy (`privacy.md`): EU users' personal data is stored in the EU (database, backups, uploaded files, logs). An edge proxy or CDN that only passes traffic through may be outside the EU when it is a listed processor with a data processing agreement and a transfer basis, and caches no personal data; the plan names an EU-based alternative next to it. `security.md`'s edge protection links to this, which resolves the conflict between the two references.
- Multi-tenant data (`backend.md`): an app planned for several organizations is multi-tenant from its first migration, even with one tenant at launch. Repositories always filter by tenant, with cross-tenant tests. Row Level Security is a second layer, with a pattern for self-hosted Postgres: a non-owner app role, the tenant set per transaction with `set_config(..., true)` so pooled connections are safe, policies that match nothing when it is missing, and a separate role for work that spans tenants. The security tests row includes policy and cross-tenant tests.
- Diagrams (`architecture.md`): the system diagram is drawn top-down, so it stays readable on a phone.
- Root `CLAUDE.md` template: the Data and Privacy summary lines carry the above.
